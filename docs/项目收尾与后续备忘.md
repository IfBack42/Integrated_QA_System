# Integrated QA System 项目收尾与后续备忘

封版日期：2026-11-24

## 1. 当前结论

本项目已完成从教学基线到本地工程原型的主要重构，当前进入**封版状态**。

接下来只学习课程中的FastAPI服务化与部署概念，不再继续扩展当前项目功能。部署课程看完后转入下一个项目；本文只保存已完成事实、当前边界和未来若重新启动项目时的思路。

项目当前定位：

```text
可复现的本地多层检索问答原型
≠ 已上线生产系统
```

## 2. 已完成的核心能力

### FAQ链路

```text
MySQL权威FAQ
→ FAQSnapshot与SHA-256内容版本
→ Redis Hash正式副本
→ Redis Search中文全文索引
→ BM25可靠命中判断
```

- MySQL是正式FAQ的唯一权威来源。
- Redis正式FAQ可以从MySQL重建，版本一致时跳过刷新。
- FAQ使用Redis Search相似检索，不再依赖原始query精确匹配。
- 正常未命中、低分、无效输入和基础设施异常使用不同语义处理。
- FAQ命中后直接返回Redis正式文档中的审核答案。

### RAG链路

```text
FAQ未命中
→ Redis临时RAG答案缓存
→ BERT意图识别
→ 检索策略选择
→ BGE-M3稠密/神经稀疏编码
→ Milvus混合召回
→ parent_id恢复并去重父块
→ CrossEncoder重排
→ LLM依据资料生成答案
```

- 支持TXT、Markdown、PDF、DOCX、PPTX与图片OCR加载接口。
- 完成父子分块、稳定块ID和Milvus入库。
- 完成稠密/神经稀疏双路召回、WeightedRanker融合与CrossEncoder重排。
- 支持直接检索、HyDE、子查询和Step-back策略。
- 完成BERT意图分类训练、推理和新旧模型评估。
- 完成FAQ、临时缓存和RAG的统一项目级返回对象及资源关闭流程。
- 临时RAG缓存具有独立前缀和TTL，不进入正式FAQ索引，也不修改FAQ版本。

### 评估链路

- 已实现通过真实系统入口采集答案、上下文和耗时。
- 已实现RAGAS评分与最终报告生成。
- 当前24条小规模黄金集只作为本地版本基线，不外推为线上效果。

## 3. 当前工程边界

以下内容尚未实现，但不阻塞本项目作为学习、简历和面试展示原型收尾：

- 没有Web/API、多用户、鉴权、并发压测和线上监控。
- 没有把对话历史持久化为多用户会话。
- 历史对话只参与最终提示词，没有在检索前改写当前query。
- FAQ的`35.0`最低BM25分来自少量人工观察，尚未用独立FAQ测试集系统校准。
- `file_path_filter`链路尚未完成完整验证。
- 自动化单元测试与数据库集成测试不足。
- Redis正式副本目前依赖版本Key判断，没有逐条完整性审计工具。
- 仍有少量教材术语问法可能被BERT高置信度误路由。
- 相似章节和重复标题仍会干扰个别长文档召回。

这些内容应在README、简历和面试中作为明确边界说明，不能描述成已经完成。

## 4. 部署课程只学习什么

部署课程阶段只补概念，不再对当前项目进行大规模改造。

建议掌握：

- FastAPI请求、响应与Pydantic模型。
- 统一API如何调用`QASystem`，而不是绕过总业务入口直接访问内部Retriever。
- 普通HTTP返回与SSE/WebSocket流式输出的区别。
- 健康检查、超时、统一异常和资源关闭。
- Uvicorn如何启动FastAPI应用。
- 本地服务化与真正生产部署之间的边界。

暂不实施：

- Docker、Kubernetes和GPU调度。
- 多进程模型服务、任务队列和高并发优化。
- 登录、权限、限流和持久化多用户会话。
- 前端页面与管理后台。

## 5. 后续备忘：基于历史改写检索Query

### 问题

单纯把历史拼进最终提示词，只能帮助LLM生成答案，不能改善前面的Redis Search或Milvus检索。

例如：

```text
第一问：人工智能课程大纲是什么？
第二问：那有什么推荐的学习路线？
```

第二问脱离历史后不完整，检索前应改写为：

```text
人工智能课程有什么推荐的学习路线？
```

### 正确职责

Query改写不属于RedisClient。Redis只负责检索已经能够独立理解的文本。

未来若重新开发，可增加：

```text
ContextQueryRewriter
输入：original_query + 最近必要历史
输出：可独立理解的retrieval_query
```

完整数据流：

```text
original_query + history
→ 判断当前问题是否依赖历史
├─ 不依赖：retrieval_query = original_query
└─ 依赖：LLM改写为独立问题
             ↓
retrieval_query
→ Redis Search正式FAQ
├─ 命中：返回权威答案
└─ 未命中：意图识别、策略选择和Milvus检索
             ↓
original_query + history + 检索资料
→ LLM生成最终答案
```

必须同时保留：

- `original_query`：用户真实表达，用于最终回答、日志和评估。
- `retrieval_query`：只用于提高FAQ和RAG检索效果。

### 成本控制

这项功能通常需要额外LLM调用，但不应每个问题都改写。

未来第一版可按需触发：

```text
history为空
→ 不改写

query信息完整
→ 不改写

存在history，且query含有明显指代或省略
例如：那、这个、它、还有呢、怎么学、为什么这样
→ 使用低成本模型改写
```

其他控制措施：

- 只发送最近必要历史。
- 使用低温度和很小的输出上限，只返回一个独立问题。
- 改写失败时记录警告并回退原始query，保证系统仍可使用。
- 接入前建立上下文追问测试集，对比FAQ命中率、Context Recall、额外延迟和调用成本。
- 在上下文请求指纹完成前，带history的请求继续绕过临时答案缓存。

这项能力属于以后重新启动项目时最值得优先实现的功能，但不纳入当前封版范围。

## 6. 其他未来方向

以下方向只保留记录，不安排当前开发：

### 人工审核沉淀FAQ

```text
RAG生成答案
→ Redis临时缓存
→ 可选待审核记录
→ 人工通过、修改或拒绝
→ 通过后写入MySQL正式FAQ
→ 刷新Redis正式副本
```

未审核的LLM答案不能进入正式FAQ索引。

### 小说与长文档业务

- 为书籍、卷、章节和顺序增加稳定元数据。
- 根据阅读进度构造Milvus过滤条件，防止跨书检索和剧透。
- 审核后的FAQ同样绑定可见章节范围。

### 有证据再实施的性能优化

- FAQ测试证明BM25无法覆盖语义改写后，再评估Redis Search稠密向量混合检索。
- 全量同步真实拖慢启动后，再考虑MySQL→Redis增量同步。
- 父块重复存储成为真实瓶颈后，再考虑独立DocStore或父块Collection。
- 需要多人或跨设备恢复历史后，再设计Redis/MySQL会话持久化。

## 7. 当前明确不做

- 不为了展示LangChain而强行接入LangChain Memory。
- 不给临时RAG答案建立正式Redis Search索引。
- 不把正常未命中、网络故障和结果结构错误统一返回`None`。
- 不在没有评测证据时同时调整分块、Top-K、权重、阈值和提示词。
- 不提前引入微服务、消息队列、复杂增量同步或双Collection架构。
- 不把课程演示的`session_id + MySQL`视为高价值会话智能。
- 不把FastAPI封装接口描述成完整生产部署。

## 8. 项目交付口径

可以准确描述为：

> 在课程RAG基线之上，完成MySQL权威FAQ、Redis Search BM25、临时RAG缓存、BERT意图识别、BGE-M3稠密/神经稀疏编码、Milvus混合召回、CrossEncoder重排和LLM生成的多层问答链路，并建立真实系统结果采集与RAGAS小样本评估流程。

需要同时说明：

> 当前版本是经过本地真实链路验证的工程原型，尚未实现Web/API、多用户、并发压测和生产监控；评测结果来自24条小规模黄金集。

## 9. 如果以后重新启动项目

恢复开发时按以下顺序，不需要重新推翻架构：

1. 先重新运行当前主链路与评测基线。
2. 补关键自动化测试。
3. 单独实现并验证`ContextQueryRewriter`。
4. 校准FAQ阈值和Top-1/Top-2分差规则。
5. 再根据真实业务选择API服务化、人工审核或小说章节过滤。

在此之前，当前项目保持封版，不再追加功能。
